F2: Multipart filename sanitized before HTML-unescape, allowing path separators to be reintroduced
==================================================================================================

The uploaded filename from the attacker-controlled Content-Disposition header is passed through os.path.basename() (line 215) BEFORE html.unescape() (line 217); html.unescape can reintroduce '/' (e.g. '&#47;') and path components after basename has already run, so the value handed to upload handlers can contain traversal sequences.

Impact: The parser emits file names such as '../../../x' or '..' from crafted/HTML-encoded Content-Disposition filenames. This is the weakness class behind CVE-2021-31542 (this snapshot dated 2021-04-06 predates the May 2021 fix that reordered sanitization and added validate_file_name). Whether traversal reaches the filesystem depends on downstream consumers; django/core/files/uploadedfile.py re-applies os.path.basename (neutralizing embedded '/'), but a name of exactly '..' still passes through both basename calls and can cause directory traversal when the application saves the file under uploaded_file.name via Storage.

Exploit scenario: An attacker submits multipart/form-data with Content-Disposition filename='..' (or an HTML-encoded separator sequence). The parser produces file_name='..', which survives UploadedFile._set_name's basename. An application that saves the upload using the provided name (a common pattern) then writes/overwrites a path one directory above the intended upload location.

Recommendation: Apply html.unescape and force_str before os.path.basename, and explicitly reject names that are '.', '..', or contain path separators (as done by the later validate_file_name fix).

# F2: Multipart filename sanitized before HTML-unescape, allowing path separators to be reintroduced

**Status:** patch written -> `F2.patch`

**Verified by a panel of agents.** An independent verifier reviewed the change against the finding and stated the three claims below with confidence, and a second, fresh reviewer re-challenged the bare diff for new vulnerabilities. The patch was written only because the panel could vouch for it; nothing here was applied for you.

MultiPartParser.parse ran os.path.basename on the Content-Disposition filename before html.unescape, so an HTML-encoded separator was decoded into a real '/' afterwards and '.'/'..' were never rejected; the patch replaces IE_sanitize with sanitize_file_name, which decodes entities first, strips everything up to the last '/' and '\', keeps the existing whitespace strip, and returns None for '', '.', and '..' so the part is skipped, with the IE_sanitize name kept as an alias and the unused os import removed.
